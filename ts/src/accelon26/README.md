# accelon26 — 純瀏覽器 mockup（無伺服器、無 sidecar）

```bash
cd ts
bun run tools/build-viewer.ts        # -> ../build/accelon26.html（單檔，可雙擊開啟）
bun run test/accelon26.test.ts --adb D:\accelon3\yinshun\yinshun.adb
bun run tools/browser-test.ts --adb D:\accelon3\yinshun\yinshun.adb
```

## 三個檔案

| 檔案 | 角色 |
|---|---|
| [src/accelon26/adb.ts](src/accelon26/adb.ts) | 解析核心。只用一個原語 `AdbIO.read(offset, length)`；`BlobIO`（瀏覽器 `File`）與 `SyncIO`（Bun 測試）互換 |
| [src/accelon26/viewer.ts](src/accelon26/viewer.ts) | 三欄 UI（原生 DOM，無框架） |
| [tools/build-viewer.ts](tools/build-viewer.ts) | 把 UI bundle 成**傳統 script 並 inline** 進單一 HTML |

## 之後的 Go + mmap 切口（Wails3；已安裝，暫不使用）

現在刻意用 `file://` 單檔，因為改 UI 最快。等 UI 定稿後，**效能攸關的部分換成 Go + mmap**，
這個 mockup 的架構已經先備好切口：

| 現在的邊界 | 換成 Go 時 |
|---|---|
| `AdbIO.read(offset, length)`（唯一原語） | Go 端 `mmap` 直接切片；`BlobIO` 退役 |
| `AdbReader` 的容器／長度表解析 | 已在 Go：`internal/adb/format.go`、`packedlist.go` 有舊版可作起點（需同步新規則） |
| 純 JS bzip2（每塊 1.2–4.4 ms） | Go 端 `compress/bzip2` 或 libbz2；這是目前最大的 CPU 熱點 |
| `VaPaMapper` 的 walk（13j 全走 0.35 s、yinshun 3 s） | mmap + 原生迴圈，且可只在需要時走 |
| UI（原生 DOM，無框架） | Wails3 的 WebView 直接沿用；不再受 `file://` 限制，可拆 ESM、可用 worker |

要注意的三件事：

1. **語意要照抄**：`textSpan`（跨區塊拼接＋夾長度）、`lineSpans`（跨行塗紅）、
   `costOf`（開／閉標籤 +4、skip 標籤 0）——這三處是最容易在改寫時走鐘的地方，
   `test/vapa.test.ts` 與 `tools/verify-vapa.ts` 應一起搬去當 Go 的驗收。
2. **`blocksVirtual` 是 ground truth，不要自己推**：區塊起始 VA 一律取
   `tables/blocks.virtual`（實測：跨界元素的 VA 與 stored 值差 1，推公式會錯）。
3. **瀏覽器的兩個快取在 Go 版會變成多餘**：`srcTextCache`（解壓快取）與
   `docCache`（行視窗快取）。mmap 之下直接讀，反而要改回「不留快取」以免吃記憶體。

## 為什麼要「單檔 + inline script」

`file://` 的限制（ES module、`fetch`、worker、`localStorage`）與單檔設計約束見 [yap-software-practice.md](../../../yap-software-practice.md) §3。

本專案因此用傳統 script 全部 inline；資料由使用者挑檔（`<input type=file>` 或拖放），靠 `File.slice().arrayBuffer()` 隨機讀取，整個檔案不會進記憶體。

## 隨機讀取的成本（實測）

**結論：`file://` 的開檔成本幾乎全在「讀取次數」而不是位元組數。**
2024 版量測（yinshun 23.76 MiB）：

| 項目 | 修正前 | 修正後 |
|---|---:|---:|
| `Blob.slice()` 呼叫次數 | **10,489** | **19** |
| 實際讀取位元組 | 0.89 MiB | 2.06 MiB |
| I/O 時間 | **3,469 ms** | **15 ms** |
| 開檔總計 | **3,525 ms** | **60 ms** |
| 快取命中（未再讀 blob） | 0 | 10,473 |

每次 `Blob.slice().arrayBuffer()` 約 **0.33 ms**，與長度無關 —— 10,489 次 × 0.33 ms ≈ 3.5 s，
**這才是「24 MB 檔案開 5 秒」的原因，不是 SSD、也不是解壓縮或解析**。

碎讀的來源：容器名稱表逐名讀（`parseContainer` 每個名稱一次）、`attributeValues()` 每個值一次
（yinshun 有 76 個屬性鍵、每個又是容器，值數以千計）。

**修法**：`BlobIO` 加一層 128 KiB 區塊快取 —— 小讀取（≤ 32 KiB）先取所在的 128 KiB 視窗
（一次 blob 讀），之後同一視窗內的小讀取直接 `subarray`。快取上限 64 個視窗。

修正後的細分（`state()`／`openBreakdown()` 可查，狀態列也會顯示）：

| 階段 | 13j | yinshun |
|---|---:|---:|
| 解析容器（`AdbReader.open`） | 9 ms | 12 ms |
| token 索引 | 1 ms | 2 ms |
| VA 表（+ 錨點） | 5 ms | 15 ms（錨點另 18 ms） |
| 文件清單 | 0 ms | 0 ms |
| **開檔合計** | **26 ms** | **60 ms** |
| 背景目錄樹（不阻塞開檔） | 353 ms | 0 ms（13j 要讀 2020 個標籤） |

也就是 UI 在 **60 ms** 內就能用；剩下的目錄樹是背景建立。

| 動作 | 讀取量 |
|---|---:|
| 開檔（header + 容器頭 + 長度表 + 名稱表） | yinshun 約 130 KiB、13j 約 40 KiB |
| token 索引（名稱 + posting 位元組長度） | 0 額外 payload（長度表已在開檔時讀完） |
| 單一 posting list | 該區塊（最大 6.4 MiB，lawtw） |
| 單一 source 區塊（解壓） | 8–14 KiB 壓縮 → 16 KiB 文字 |
| 單一圖片 | 該區塊（resources 未壓縮） |

`Blob.slice` 每次呼叫約 0.01 ms（實測），所以逐區塊讀取非常便宜；
貴的是**解壓**：純 JS bzip2 每塊 1.2–4.4 ms，所以只解當前需要的區塊。

## 這一輪測試抓到的真 bug

1. **`TextDecoder('utf-16le')` 會把未配對代理換成 U+FFFD**（Bun 實測；瀏覽器實作不一）。
   13j 第 15 個 token 是 `⿱艹` + `U+D85A`，必須逐碼元自建字串才保真 → 改用 `decodeUtf16()`。
2. `renderMeta` 少傳一個參數 → `undefined.toFixed()`（只在文件清單載入後才炸）。
3. 文件清單要 `blocks.virtual`，原本沒先載入 → 文件永遠是 0 筆。
4. 456 張縮圖逐張讀會卡住首屏 → 限制 48 張並讓出事件迴圈。

## 介面（2026-02 改版）

* **字級**加大：內文 15px、token 列 17px、命中文字 16px；標題 **accelon26**（醒目色）。
* **本文可調字級**（右側工具列 `−`／`＋`／`不換行`／`預設`）：
  * 存 localStorage（`accelon26.docfs`）；
  * **「不換行」**的兩個關鍵：
    1. **可用寬度取中間欄**（`docTextWidth()`）——`main` 是 grid，左／右欄各佔一份，
       所以寬度要讀 `.docBody` 的 `clientWidth`（已扣掉側欄與自己的捲軸）再扣列內 padding/gap。
    2. **量測必須在無寬度約束的容器裡做**——把探針放進 `.docBody`（`overflow:auto`）會被**裁到欄寬**，
       100px 字級的 20 個漢字實際 2000px 卻只量到 800px，換算出的字級會爆到上限
       （實測就是這個 bug：算出 40px、溢出 1450px）。改成 `position:fixed;left:-100000px` 的量尺。
    3. 上限只約束「常見長行」（≤1.4×P90）：yinshun 有單行 96 字元對 P90=45，
       若以最長行封頂會把整份文件壓到可讀下限 14px；超長行改為橫向捲動。
  * 實測：13j 左欄開 14px → 左欄收 17px；yinshun 16px → 22px（皆正確扣除側欄）。
* **posting list 預設不顯示**，點 token 之後才出現。
* **載入後**：檔案按鈕隱藏，改點 header 的**中文庫名**開啟別的資料庫。
* **欄位功能**：**左 = 全文搜尋 ＋ token ＋ posting list**，**中 = 文件文字（不顯示行號）**，**右 = META／容量／文件／圖片 分頁**（**預設關閉**）。
* **全文搜尋（詞組）**：輸入即時搜尋（不必按 Enter，每次輸入重跑；posting list 依 token 快取，
  多打一個字只付新 token 的區塊讀取）。語意照 Delphi：query 用**同一個 tokenizer** 切詞，
  詞與詞之間是 `OP_AND`，而 `TPhraseHits.nextmatch` 要求**VA 連續** —— 所以「象曰」是詞組，
  不是兩個字的集合；因為硬換行不佔 VA，跨行的詞照樣命中。
  搜尋摘要向外讀到**標點**為止（左右上限 80/160 字），摘要**不顯示 VA／行**；點摘要即跳本文並標紅。
* **搜尋分群統計**（`<樹>` 的第一層，13j／yinshun 都是 `書`）：
  搜尋摘要上方一排 chip（`全部` ＋ 各書的命中數，點一下只看該書）。
  分群用 `groupHits()`：書的 VA 遞增，所以每個命中用二分搜尋定位所屬實例，與引擎把命中歸樹的方式相同。
  涵蓋範圍外的命中（極少數）不計入任何群，因此**各群合計 ≤ 命中數**（實測 13j 446/446、yinshun 5000/5000）。
* **兩種模式**（header 的「進階」鈕，狀態存 `accelon26.advanced`）：
  * **預設（讀者視角）**：左欄只有**全文搜尋**；右欄第一分頁是**目錄**（此庫的缺省目錄），
    一開始就載入**第一個有 `t=` 的 `<樹>`**。
  * **進階**：左欄多出 **token** 分頁，右欄多出 **META／容量／文件／圖片**。
  * 關閉進階時會自動回到預設分頁（搜尋／目錄）。
* **posting list 面板已移除**：點 token 直接讀它的 posting list 並跳到第一筆命中。
* **目錄樹（`<樹>` 分頁）**：每個 `<樹>` 一個分頁（右欄「目錄」）。
  * **分頁名＝`<樹>…</樹>` 的文字**（作者的 `ss.caption := removetag(getnNodeValue(dn))`），
    不是從 `s=` 推導：taisho 的七棵樹叫 經目／書名／分書頻次／分卷／分卷頻次／西文／反連結，
    而 `s=` 只有 `*`／`$書`／`*書`／`*卷`／`~00602000`／`%` 六種。取不到文字才退回 kind 的預設名。
  * **分頁集合永遠來自「`<樹>` 宣告」**（`session.trees`，開檔就有），不是來自已建好的 `dirTrees`
    —— `dirTrees` 只放 `s="*"` 的樹，拿它當分頁來源會在背景建樹完成時把名詞／頻次／西文全部藏起來
    （2026-10-20 修：taisho 宣告 7 棵、畫面只剩 目錄＋token）。
  * **同一個 pane 被宣告多棵時**（taisho：經目＋分卷都是 `s="*"`；分書頻次 `*書` ＋ 分卷頻次 `*卷`），
    pane 上方出現下拉 `#dirPick` / `#freqPick`，宣告不會被默默丟掉；只宣告一棵時下拉隱藏。
  * **`樹.t`／`樹.s` 是稀疏的屬性表**：只有帶該屬性的實例才有值，值裡的 pointer（`0xTT00NNNN`）
    才是實例序號。照位置讀會把 分卷 的 `t=` 讀成 經目 的 `t="冊,書,品."`（同一棵樹畫兩次）。
  * **adb 的標籤幾乎都是兄弟節點**（只有 `<檔>` 是為了過 XML validator 而巢狀），所以層級**不可能**從標記推出來 ——
    這正是「同一份資料可以呈現成不同的樹」的原因。
  * 層級來自 **`t=` 的層級鏈**：`<樹 t="書">` 是入口層，`<書 t="章,節,項.">` 宣告接下來三層。
    yinshun 的 `書.t` 有 20 餘種值，所以「每個 `<書>` 各自宣告」也是合法的。
  * **`t=` 是逐實例的宣告**：每個 `<書>`（及其他標籤）都能自己指定 `t=""`；
    **沒指定就不再往下探**（到下一個 `<書>` 為止）。13j 只有第一個 `<書>` 帶 `t="章,節,項."`，
    所以嚴格說只有「周易」那一支有四層；其餘 12 本依規則不再往下。
  * 載入時會把「某標籤第一個實例的宣告」當成該標籤的預設（13j 因此得到完整的四層），
    但這是**寬鬆處理**，不是規格原文。
  * **`章`/`節`/`項` 自己沒有 `t=`**：最後一個宣告裡剩下的層級會自動成為連續的下一層
    （13j → `L1=書 → L2=章 → L3=節 → L4=項`）。**不在 `t=` 裡的標籤（`頁`/`頁元`…）不得進樹**。
  * 歸屬規則是「**文件順序中，最近的前一個上層節點**」，不是 VA 包含：節點範圍只到「同層下一個節點」為止，
    父節點範圍會撐開以涵蓋子節點（但不會吃掉下一個同層節點）。
  * 實測：13j `L1=書×13 L2=章×259 L3=節×1,448 L4=項×300`，**2,020 個節點全部入樹**；
    yinshun 五層 `L1=書×44 L2=8 L3=510 L4=1,570 L5=1,091`。
  * 顯示：緊湊單行（不隨深度增加留白），深度用 **HSV 30% 亮度**的色點表示，`▸`/`▾` 展開收合，
    收合時右側顯示子節點數；點節點列本身會聯動本文。
  * 標籤解析：子標籤的 `n=`（13j：`<書 … id="周易"><頁元 n="周易"/>`）優先，其次取節點**開頭的內文**
    （yinshun：`<書 t="部" id="2">般若經講記</書>`）。`t=` 是層級宣告、`id=` 可能只是序號，兩者都**不可**當名字。
* **搜尋範圍 `s=`**（依格式作者說明實作 `parseScope()`）：
  | `s=` | 意義 | 現況 |
  |---|---|---|
  | `*` | 全文檢索 | ✅ 已實作（分群依 `t` 第一層） |
  | `~00602000` | 只檢索碼點 U+0060–U+2000 開頭的 token | 已套用（左欄「西文」分頁） |
  | `$詞` | 列出 `<詞>` 包住的文字，允許 tofind 出現在詞首／中／尾 | ✅ 已實作（「名詞」分頁；點詞條＝只讀那一個 `<詞>` 的內文） |
  | `*u=文` | 以 `<文>` 分段：摘要顯示**段名**（`<文>…</文>` 之間的文字）與該段命中數 | ✅ 已實作（「頻次」分頁） |
  | `*詞` | 以 `<詞>` 分段：同一個 pane，頁名「全文」；點段＝只讀那一個 `<詞>` | ✅ 已實作 |
* **全頁不捲動**：`html, body { height:100%; overflow:hidden }`，`body` 是 `auto 1fr` 的 grid，
  所以只有面板自己捲（文件內容、搜尋摘要、token 清單、目錄樹）。

## 目錄樹：已驗證的結果與待定的規則

**已驗證（13j，`tree.test.ts` 22/22 ＋ `file-protocol-test.ts` 54/54）**

```
L1=書×13  L2=章×259  L3=節×1,448  L4=項×300    2,020 個節點全部入樹
13 根（書）＝周易 尚書 毛詩 周禮 儀禮 …, 各書章數 69,4,6,6,17,50,12,12,12,20,18,19,14（合計 259）
UI：預設 13 列收合 → 展開周易 = 82 列（章 乾 坤 屯 蒙…）→ 展開章 = 86 列（節）
    深度色點 rgb(106,57,57) 書 → rgb(126,119,37) 章，點節點列會聯動本文
```
69 個節點有子節點；`乾`/`坤` 本身沒有 `節`（整章就是卦辭），所以不是每章都能展開 —— 這與資料相符。

**規則（已定案，2024 修訂）**

* `t="章,節,項."` 的**第一項是直接子層**（章），其餘（節、項）是**同一父層下的兄弟槽位**：它們依
  **文件順序**依序歸屬，所以 `節` 接在 `章` 後面、`項` 再接在後面，全部都掛在同一本書之下。
* **尾點 `.` 表示「到此為止」**：子層本身仍然下探（書 → 章），但**不再往更深一層**（章 不再下探到 節/項）。
  這與「每層只取第一項」合起來就是：13j 的樹是 `書 → 章`，`節`/`項` 只作為兄弟槽位存在。
* 沒有 `t=` 的實例**完全不下探**（到下一個同標籤為止）。
* **只出現在 `t=` 裡的標籤才可能進樹**；`頁`/`頁元`/`集` 這類沒被任何 `t=` 點名的標籤不進樹。

**作用範圍（realm）—— 這條最重要**

`t=` 的子孫**只作用到下一個同樣的標籤之前**；沒有下一個同樣的標籤就到 `</檔>`。而且

> 標籤本身可能是錯的，不能盡信；`t=` 只是宣告**可能的**層級關係。

所以實作上是「先找順位、再由宣告決定它是不是子層」，而不是反過來：

1. 每個實例的 `t=` 只在自己的範圍內有效 —— 範圍結束於**下一個同樣的標籤**（不是任何標籤）。
2. 範圍內的下一個實例若落在宣告的層級上，就是它的子節點。
3. 宣告只是「可能關係」，因此找不到對應實例時不會報錯，只是沒有子節點。
4. 子節點的搜尋邊界就是父節點範圍，所以不會跨到下一個同樣標籤之後。

這正是目前的實作（`materialize` 以父節點的 `vaEnd` 為搜尋上界，而 `vaEnd` 就是「下一個同樣標籤」），
13j 因此得到 `書 → 章`，且 69 章全部落在第一本的範圍 `[29, 27685)` 內（27685 就是下一本 `<書>`）。

| yinshun | `L1=書×44`（般若經講記 寶積經講記 … 附錄）`L2=記/部/章/編/節/文` `L3=章/部/節/甲/序/頌/年/論/經` `L4=節/甲/時/一/章`；44 本全部可展開 |

**兩庫的 `書` 語義不同**（實測）：

* **13j**：`<書 t="章,節,項." id="周易">周易</書>` —— 標題式（書名緊接在標籤後，立刻 `</書>`）。
* **yinshun**：`<書 t="部" id="2">般若經講記</書>` —— 前 44 個是標題式，但**後面還有 metadata 型的 `書`**
  （出版社、版次、年月），所以書名會取到出版資訊；這類節點名稱會退化成 `#N`。

**標籤層級預設**：宣告只寫一次（13j 的 13 本只有第一本帶 `t=`），其餘同標籤實例沿用；
子層的**兄弟槽位**（節、項）會**繼承到下一個層級**，所以 `章` 即使沒有自己的 `t=` 也能收 節/項。



## 目錄樹的資料模型：自訂標題（h1~h6 的推廣）

格式作者對 `<樹>`／`t=` 的說明：

> 這個設計接近 HTML 的 `<h1>`~`<h6>` 語義，我讓標題可以自定義。精神是一致的：讓用戶很容易做語義標記
> （**一行可見開始及結束**，渲染也容易），實務上 h1~h6 的限制太大了。

這解釋了整個模型，也解釋了為什麼「都是兄弟節點」：

| HTML | adb |
|---|---|
| `<h2>第一章</h2>` ＋ 內文 ＋ `<h2>第二章</h2>` | `<章>乾</章>` ＋ 內文 ＋ `<章>坤</章>` |
| 層級固定 h1~h6 | 層級由 `t="章,節,項."` **自訂**，可有多組（每個 `<樹>` 一組） |
| 標題的範圍＝到下一個同級或更高級標題 | 標籤的範圍＝**到下一個同樣的標籤**（沒有就到 `</檔>`） |
| 標題不「包住」內容 | 標籤不包住內容 —— 這是**一行可見開始及結束**的關鍵 |

**可驗證的不變量**（已加入 `test/tree.test.ts`）：

```
沒有「同標籤互相巢狀」（不會出現 <h2> 包 <h2>）      13j 0 個、yinshun 0 個
文件順序不變（子節點的 VA 一定大於父節點）            13j 0 個違反、yinshun 0 個
深度遞增正常                                         兩庫皆 true
```

## 目錄樹的資料來源（設計原理：不掃內文）

格式的設計意圖是**盡量不掃內文就能取得結構資訊**，所以：

| 資訊 | 來源 | 是否需要掃內文 |
|---|---|---|
| 有哪些樹 | `attributes/樹.s`、`attributes/樹.t` | 不用（屬性容器） |
| 每個標籤的實例與 VA | `tags` 容器（開／閉標籤**各是一個條目**） | 不用（packed list） |
| 各層的 VA 位置 | `tables/blocks.virtual` | 不用（長度表） |
| 每個實例的 `t=` | `attributes/<標籤>.t` | 不用 |
| 節點顯示名 | 13j：`attributes/書.n`（`書.id` 是序號）<br>yinshun：**無屬性表**，只能走內文（`<書 …>般若經講記</書>`） | 只有這一項 |

`attributeValues(key)` 回傳的 **`pointers` 就是（tag 實例序號）**：低位 24 bits 是 1-based 的實例序號
（`0x04000001`、`0x04000002`…），高位 byte 是 tag id。所以每個屬性值都能**直接對應到 `tags` 容器的哪一個實例**，
不必用 `elementAt(va)` 掃內文 —— 這是把 `t=` 讀成 per-instance 對照表的正解。

目前實作仍用 `mapper.elementAt(va)` 讀 `t=` 與名字（13j 的背景目錄樹 353 ms），
下一步應改成純屬性容器查表。

**`elementAt` 已改成查行表定位（2026-10-20，taisho 崩潰的根因）**：以前它從 block 0
逐行重播到目標 VA，並把每個 `TokenPos` 留在記憶體；taisho（241 MB、87.9 M VA）點一本排在
檔尾的書要 **> 25 s、3.8 GB**（16 GB 桌機的 WebView2 直接「內存不足」）。現在用
`tables/lines.virtual`（每行start＝`lines.virtual[i-1] + 1`）二分找行、單獨 tokenise 一行，
遠端查詢 **4.5 ms**、整個程式的堆 < 100 MB。逐行重播只留給驗證工具。
`tools/check-element.ts` 對拍：每個標籤實例的 VA 都回到自己（13j／yinshun／fgdict／taisho 全過）。

**命中數不從清單算（同日）**：搜尋結果只留前 5,000 筆，而且是 VA 順序的前綴（taisho「佛」
567,678 筆 → 前 5,000 筆全在第一冊）。目錄徽章、頻次分段、點徽章之後的摘要都改用
`SearchSession.rangeStats()`／`hitsInRange()` 直接對 posting 清單二分（`matchesInRange()`，
與 `phraseMatchPattern()` 同一套規則），所以 56 個冊的徽章加總正好是 567,678。

1. **13j 的 `<書>` 是自閉標籤**（`<書 t="章,節,項." id="周易">周易</書>`），`<章>` 是它的**兄弟**而非子節點；
   目前建樹以 VA 涵蓋範圍為界，所以 13j 只長出 7 根 / 118 節點（13 個 `<書>`，其中 6 個蓋到後面的章節）。
   需要向作者確認：自閉標籤的節點，其子節點範圍該以什麼為界。
2. yinshun 的 `書.t` 有 20 餘種值（`記`/`部`/`章,節.`/`章,節,項,目,干.`…），逐實例遞迴已可運作，
   但 345 個 `頌` 仍落在根層（宣告它的上層標籤尚未載入）。
3. `s="*u=文"` 的第三棵樹要用 `<文>` 分段顯示「段名 + 該段命中數」；`~00602000`（碼點範圍）與
   `$詞`（`<詞>` 包住的文字，允許 tofind 出現在詞首／中／尾）已解析但尚未套用於檢索。
4. 依作者說明，**`tags` 容器與 `tables/blocks.virtual` 已足以建樹**（開／閉標籤都各自是一個 tag 條目），
   目前實作仍在讀內文取名字，應改成純粹用 tag 條目與屬性指標（`attributeValues()` 的 `pointers` 已帶著
   每個屬性的 tag id ＋實例序號），可省掉大量來源區塊解壓。
* **點 token／摘要 → 聯動本文**：跳到該位置、標出該行，並**只塗紅那一個 token／整個詞組**。
  塗紅用 `mapper.phraseSpans()` **逐 token 檢查 PA 是否相接**，所以：
  連續的字會框成一整段；被**硬換行**切開的詞會在兩行各塗一段（合起來仍是完整詞組）；
  兩字之間夾標籤時（`象<頁 n="2"/>曰`）只塗文字、不把標籤框進去。
* **欄寬可拖曳**：預設左 25 / 中 75 / 右 0（右欄關閉），兩側各有拖曳把手；
  拖到 **15% 以下自動隱藏**（存成 0），把手雙擊回復 25%。收起的那一側會記住
  **上回調整的寬度**（`last`），按 ◧／◨ 打開就回到那個寬度，不是回到 25%。狀態（含開啟／關閉）
  存在 localStorage（`accelon26.cols.v2`），首次載入即寫入；視窗 < 900px 時兩側自動收起。

## file:// 模式的實測（現行目標：只支援 13j 與 yinshun）

不用伺服器、不用 sidecar：**雙擊 [build/accelon26.html](../../../build/accelon26.html)，選檔即用**。
`tools/file-protocol-test.ts` 是真的把頁面用 `file://` 開起來、再用檔案輸入餵入 .adb 的測試：

| 檢查 | 13j | yinshun |
|---|---|---|
| 頁面確實跑在 `file://` | ✓ `file://(none)` | ✓ |
| `fetch` 在 `file://` 不可用（確認走 File API） | ✓ blocked | ✓ |
| 經 `Blob.slice` 開檔 | 1.3 s | 5.0 s（23.76 MiB） |
| token 索引（只讀名稱表＋長度表） | 1 ms | 2 ms |
| VA 表（blocks.virtual＋標籤錨點 170,428 筆） | 25 ms | 111 ms |
| 文件清單（45 篇） | — | 59 ms |
| 首次 posting 定位（含從頭 walk 到該區塊） | 250 ms | 427 ms |
| UI 渲染、資源縮圖、無例外 | ✓ | ✓ 456 資源前 48 張 |

結論：**可行，13j 幾乎即時；yinshun 開檔約 5 秒**，瓶頸是 `Blob` 讀取 23.76 MiB 本身，
不是解析（解析全部 < 200 ms）。首次點 posting 的 0.25–0.43 s 是惰性 walk，同一區塊內
再點就快取命中。

### file:// 的三個硬限制（設計已配合）

通用限制與單檔約束見 [yap-software-practice.md](../../../yap-software-practice.md) §3。本專案因此用傳統 script 全部 inline、資料由使用者選檔／拖放、`File.slice()` 隨機讀取；自動化測試用 `--allow-file-access-from-files`，正常使用時「使用者手動選檔」本身就授權，不需要該旗標。

## VA → PA（搜尋結果塗紅的基石）

[src/accelon26/vapa.ts](vapa.ts) 重放索引器的 VA 計數：**每個入索引 token +1、每段空白 +1、
標籤 +4、skip 標籤（`isSkiptag`：`頁 聯 註 圖 …`）0**。這條規則與 Pascal 的
`tokenize.pas:549 skiptokens` 一致（`tokenptr+2` 就是 `/`，所以 `</x>` 也扣 4）。
PA 只是 `blockIndex * srcblocksize + offsetInBlock`（`srcpack.pas:390 toPhysical`）。

**為何 VA 要連續**：硬換行本身不佔 VA。實測 13j 的 15,744 個行界中，**90.5% 的
VA 間距正好是 1**，所以被硬換行切開的詞仍是一個連續 VA 區間，`contextSpans()` 會
把命中沿著文字連續的後續 token 延伸成一個 span（不插入任何分隔）。13j 有 22,865 組
「VA 相鄰且跨行」的 token 對，例如「象曰」line 11→12（VA 223+224）。

驗收（`bun run`，於 `ts/`）：

| 指令 | 檢查 | 結果 |
|---|---|---|
| `test/vapa.test.ts --adb ..\13j.adb` | 區塊 VA、標籤 VA、posting 定位、跨行片語 | **13/13**（blocks 102/102、tags 4,996/4,996） |
| `tools/verify-vapa.ts --adb ..\13j.adb --max-hits 2` | 用「只出現 1–2 次」的 token 當答案對帳 | **3,006/3,006 = 100%** |
| `tools/verify-vapa.ts --adb <yinshun> --max-hits 2` | 同上 | **4,572/4,573 = 99.98%** |

不追求 100%：tokenizer 換過幾版，少數位置的空白政策不同（SPEC §15.3、§15.6），
adb 內沒有當時的 docdef 可還原。這個 mapper 的用途是**把搜尋命中塗在正確的字上**。
